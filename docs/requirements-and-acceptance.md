# Herdr Hub：需求、步骤与验收草案

状态：需求方向已获用户基本确认并授权开始工作，G1 可行性与方案阶段已通过双 reviewer 验收。
当前按经验证的 iroh 路线推进；后续实现与真实目标环境仍需逐阶段验收，不将 G1 当成产品完成。
正式验收既包括阶段性验收，也包括最终端到端验收。
持久化待办、当前状态及阶段关卡见 [工作计划](work-plan.md)；会话待办只是辅助，不是唯一记录。

## 1. 目标与范围

创建一个独立的 Rust 项目，为 Herdr App / herdr-core 提供私有、自托管的连接系统。
项目与 GitHub 仓库名称采用 `herdr-hub`，个人 GitHub 仓库由用户创建。
本地仓库目录已同步采用 `herdr-hub`。
替换连接层，而不是重新实现终端、会话、文件管理或 agent 功能。
现有 herdr-devtunnel 继续使用，不修改、迁移、重启或替换它。

预期包含三个部分：

- **服务端与管理网站**：目标部署环境为 Azure App Service，负责设备注册、身份与连接授权、在线状态、连接协商，以及必要时的中继。
- **原生 agent**：支持连接发起端、远端主机两种角色，也可同时承担两者；两端主动向服务端建立出站连接。
- **Herdr 连接适配器**：通过 `hc machine add --via` 接入，不预设需要改动 Herdr App 或 core。

发起端与远端 agent 的交互界面可以采用 **TUI**，无需桌面 GUI。
这是新项目自身的配置、配对和状态界面，不是迁回旧 Herdr TUI，也不重建终端管理器。
用户已确认首版先做 CLI，TUI 后续再加；服务端管理网站仍在首版需求范围内。
交互界面与无交互连接模式必须分离，`--via` 模式不能输出界面、提示或诊断到协议 stdout。

首版为 **单管理员自用，GitHub 登录，设备手动审批**，不实现多用户租户隔离。
管理员以预先配置的 GitHub 稳定用户 ID 识别，不采用“第一个登录的人自动认领”。
OAuth 应用注册、回调地址和部署凭据另行配置，不使用 GitHub deploy key 作为登录凭据。

连接目标是 **可直连时使用 P2P，不能直连时使用端到端加密的中继**。
用户已明确启动策略：**先经中继立即可用，能直连时自动切换**，不等待直连才开始传输业务数据。
切换过程复用成熟传输协议的顺序、去重与重传机制，不自行拼接两条独立字节流。
该自动切换仍须实测；断网或无法迁移的失败场景允许明确断开后重新连接原 core 会话。
只完成中继不算完成这一目标；企业网络阻止直连时应明确显示实际使用的路径。
“私有”首先指严格的身份与访问控制，不默认要求只能通过专用网络访问。

## 2. 功能要求

| 编号 | 需求 | 可观察的完成标准 |
| --- | --- | --- |
| R1 | Rust 原生服务与 agent | 新服务与 agent 运行不依赖 Node；具体前端构建方式另行确认。 |
| R2 | 设备注册与管理 | 设备具有稳定身份；可审批、查看在线状态、撤销访问；不能仅凭设备名称冒充已授权设备。 |
| R3 | 连接授权 | 在协商或中继配对之前完成授权；未授权、过期或重放的连接请求被拒绝。 |
| R4 | 双端主动连接 | 发起端与远端主机均可主动连接协调服务；不要求为远端配置固定公网入站端口。 |
| R5 | P2P 直连 | 在允许直连的两端环境中，真实 Herdr 数据通过直连传输，并有证据区分信令与业务数据路径。 |
| R6 | 加密中继兜底 | 直连受阻时可使用中继完成真实连接；中继不能解密业务内容，不能仅以外层 WSS 作为端到端加密证明。 |
| R7 | Herdr 协议兼容 | 保持二进制字节流、顺序、背压与方向性 EOF；日志不混入协议输出；适配器不执行任意远程 shell 文本。 |
| R8 | 会话连续性 | 可直连时从中继自动切换，并验证业务字节流连续性；不可恢复的传输断开后可重新连接原 core 会话，不重启已有终端或 agent。不承诺所有网络故障都能无缝迁移。 |
| R9 | 管理网站 | 可查看设备、在线状态、直连或中继状态，完成审批和撤销；云端注册不自动改写本机 hc 配置。 |
| R10 | 可运行与可维护 | 有持久化存储、必要的心跳和重连处理、可诊断但不泄露秘密的日志，以及清晰的启动与部署说明。 |
| R11 | macOS 与 WSL2 发起端 | 两个平台各自完成 hc 的 `--via` 接入、直连、中继回退与重连验收；不能以原生 Windows 或单一平台的结果替代 WSL2 验收。 |
| R12 | agent 界面与连接模式分离 | 发起端及远端允许采用 TUI，无需桌面 GUI；无交互 `--via` 连接不依赖界面，stdout 仅承载协议，TUI 退出行为不得违背已确认的会话生命周期。 |

首版发起端支持 **macOS 和 WSL2**，远端主机支持 **Windows Dev Box**。
根据用户当前环境说明，原生 Windows herdr-core 暂不支持 `--via`，因此不将其作为首版发起端接入方式；
Windows 上的发起端通过 WSL2 的 Linux 环境使用 hc 与连接适配器。
这不排除原生 Windows 作为远端主机运行 `hc connect`。
其他角色组合和具体验收设备另行确认。

撤销设备访问资格时，拒绝新连接并关闭已有连接；失联设备通过短期租约到期关闭兜底。
撤销不会删除文件、停止远端 core 或终止原有终端和 agent。

## 3. 工作边界

- 全部开发、构建和持久化产物保留在指定 Dev Box；不依赖原本地电脑持续在线。
- 用户已授权通过官方 rustup 安装用户级 Rust 工具链；不提权、不修改系统 PATH，不影响现有 Herdr 连接。
- 新项目与现有连接方案隔离；涉及 hc 的检查使用隔离的会话和配置，不影响正在使用的 core。
- 不自行创建 Azure 资源、发布公网服务或 GitHub 仓库、修改网络策略或安装自启动服务。
- 用户已授权在合适阶段提交并推送至现有 `herdr-hub` 远端仓库。以关键阶段双 reviewer 验收通过为提交点，由主会话提交相关代码及文档并正常推送；代码推送不等于部署授权。
- `herdr-hub` 使用专用 SSH deploy key。私钥保存在仓库之外；密钥、机器路径与真实部署信息不写入版本控制。
- 新传输连接真实设备、外部 NAT 穿透服务或部署环境前，先取得对应授权。
- 不自行决定登录方案、NAT 穿透库、STUN 提供方或额外基础设施。
- App Service 承担 HTTPS/WSS 服务，不将其当作通用 UDP STUN/TURN 主机。
- 不承诺企业网络一定允许 P2P；实际受限时必须有明确的降级结果或失败原因。

## 4. 分阶段计划与关键验收标准

以下实施顺序用于组织工作，不表示具体技术选型已经批准。
每个关键阶段均保留对应的实现、检查方法、预期结果与实际证据。
阶段 1 至 7 各有独立的双 reviewer 验收关卡，不把所有审查推迟到最后。
阶段验收只对本阶段承诺的范围作结论；未解决的阻塞项不得带入依赖它的后续阶段。

| 阶段 | 交付物与工作 | 验收标准 |
| --- | --- | --- |
| 0. 需求确认 | 确认本文、首版范围、平台与授权边界 | 需求方向、仓库名称和 macOS/WSL2 发起端已基本确认，用户已授权开始工作；未决项继续明确记录，不能将假设当成已批准要求。 |
| 1. 可行性与方案 | 比较覆盖 macOS、WSL2/Linux 与 Windows 主机的成熟 Rust 传输方案；确定连接、身份、数据流与部署方案 | 说明直连、中继、端到端认证加密和 hc 适配如何实现；评估 WSL2 网络环境对候选地址与 NAT 穿透的影响；列出必要外部依赖；在授权范围内用最小实验验证关键风险。无法验证的项目明确保持未完成。 |
| 2. 本地 Herdr 接入 | 实现原生 agent 与连接适配器，在隔离环境桥接固定 hc 会话 | 真实 hc 会话能收发二进制数据；EOF、背压、取消和子进程清理符合预期；拒绝不支持的 bootstrap；断开不终止远端原会话。 |
| 3. 控制面与设备管理 | 实现注册、审批、授权、心跳、持久化及最小管理页面 | 合法设备可上线并请求授权；非法、过期和重放请求被拒绝；服务重启后保留应持久化的信息；撤销阻止新连接并关闭已有连接，失联时由租约到期兜底。 |
| 4. 加密中继路径 | 实现经过授权的中继配对和端到端安全数据流 | 经中继运行真实 hc 会话；身份不匹配及未授权配对被拒绝；服务端不持有业务解密密钥；断连与超时后资源得到清理，缓冲受限。此阶段不能宣称 P2P 产品完成。 |
| 5. P2P 与路径选择 | 实现直连协商、从中继自动升级为直连及中继回退 | 先通过中继可用，在允许直连的两端环境中证明自动切换后业务走直连且数据连续；在可控的直连失败条件下证明中继可用；页面与日志反映真实路径。只有单机模拟或架构说明不能替代真实两端证据。 |
| 6. 故障恢复与产品整合 | 完成管理页面、状态展示、重连、撤销、服务回收与异常清理 | 覆盖网络断开、协调服务重启、单端退出及权限撤销；不误显示在线或成功；重新连接后原终端与 agent 仍在；没有无界排队或持续遗留资源。 |
| 7. 发布准备与端到端验收 | 提供运行说明、配置示例、部署产物与经过授权的跨平台实测 | 按文档分别以 macOS 和 WSL2 为发起端、Windows Dev Box 为远端完成注册、授权、Herdr 连接、直连、中继回退及重连，并记录 WSL2 网络模式；完成双 reviewer 验收。未获授权的云端部署或平台实测必须标为未验收，不能用准备好的文件替代成功记录。 |

具体性能阈值、超时、容量限制和重连策略在方案阶段提出并确认，不在此草案中凭空承诺。
各阶段按实际改动执行适当的格式、编译、静态检查及聚焦测试，不用大而空的测试数量替代验收证据。

## 5. 双 reviewer 并行只读验收

每次正式关键阶段验收时，必须：

1. **通过 Herdr App 创建两个独立 subagent 会话并行执行**，一个使用 **Copilot CLI**，另一个使用 **Pi Agent**。不以普通内部 subagent 或旧 Herdr TUI 替代。
2. 两个 reviewer 收到相同的阶段范围、需求编号、代码版本或差异快照、验收标准和证据；两者都做 review 与逐项验收，而不是一个只看代码、另一个只看功能。
3. 执行只读审查，不修改源码、配置或文档，不提交代码、安装依赖、部署或操作现有服务。额外检查不得改变被验收对象或真实环境；需要有副作用的验证，由主会话在授权的隔离环境执行并提供证据。
4. 分别给出每条标准的“通过 / 不通过 / 证据不足 / 不适用”、问题位置、影响、复现方式和依据；不能仅凭主会话的完成声明通过验收。
5. 主会话等待并读取两份结果，汇总分歧与问题。阻塞验收的问题修复后，针对受影响项重新进行双 reviewer 验收，保留前后证据。
6. 最终记录区分“实现完成”“检查通过”和“目标环境已验证”。任一 reviewer 未运行、未返回，或必要证据缺失，都不能宣称完成双 reviewer 验收。

reviewer 在各阶段达到可审查状态时启动，不仅在最终验收时启动。
每次验收须在仓库文档中记录证据索引、两份结论、主会话处理结果和复验结论，
不得仅将结果留在聊天记录或会话待办中。

## 6. 后续需要确认的决策

整体目标与工作方式已基本确认；以下细节在相关阶段开始前再确定，不要求现在一次回答：

- 首版管理网站的最低限度管理操作与登录体验。

- GitHub OAuth 应用及回调地址的部署配置、管理员恢复方式和设备审批的具体交互。
- NAT 穿透所需外部服务、Azure 部署范围和可授权的实测环境。
- 连接撤销、路径失败、重连及容量限制的具体产品语义。
